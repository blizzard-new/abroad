# 我的申請：功能整併與規劃流程 review

日期：2026-10-01。範圍是 Web 導覽、選校推薦、申請文件與日曆的使用流程；不是全專案安全／資料品質審計。本輪沒有更改後端、原生 App 或正式資料，也尚未部署。

## 發現與本輪處理

| 原本的重複／斷點 | 本輪處理 | 還需注意 |
| --- | --- | --- |
| 資格與志願、申請顧問都填學院、成績與語言 | 主入口統一稱「選校規劃」，保存的條件共用；詳細資格核對收到「其他工具」 | 詳細資格頁仍保留學系、年度、梯次與多志願等功能，因此沒有直接刪除 |
| 總覽用前端 `partnerMatch` 排名，顧問頁用後端 `_score_partner`，可能給不同的推薦 | 總覽直接顯示 `/advisor/plan` 的排序與理由；保存條件後可重新取得推薦 | 學校搜尋仍有原本的基本條件比對標籤，後續應與後端統一，避免門檻解析差異 |
| 推薦只提供查看詳情，文件目標要重新選擇 | 推薦加上「選為目標」，同時保存申請目標、加入候選並带入文件設定 | 保留其他候選，不代表已送出申請；目標更換會使文件核對失效 |
| 截止日、日曆、總覽期限摘要和多套進度卡重複 | 「我的申請」集中為填寫條件、確認目標、安排時程、準備與送件四步；官方期限來源為次要查證入口 | 四步是介面進度，不是校方錄取判定 |
| 文件填寫、文件檢查、文件庫看似同一功能 | 「申請文件」為主入口；檢查與私人文件保存為次要工具 | 三者實際用途不同：填表、核對內容、保存附件，不應刪掉實際能力 |
| 列印包每列塞滿狀態、列印資訊與份數，閱讀密集 | 文件卡片分為選取與狀態、繼續填寫、份數；附件資訊收合，提供已選／可匯出進度 | 目前版本核對、附件狀態、權限與 PDF 產生閘門仍保留 |

側邊欄主工具收斂為四個：選校規劃、候選清單、申請文件、準備時程。六個次要工具放在「其他工具」。暫停的文件改寫及重複的校內討論入口不再占據主要選單；既有頁面與路由保留。

## 已接上的規劃流程

1. 在「選校規劃」填寫學業、語言與偏好，保存條件後整理推薦。
2. 查看理由與缺口，自己確認目標學校。目標及學院／學系／學制沿用到文件工作區。
3. 在「我的申請」填申請學年度、需要時填梯次，以及每項任務的準備天數。
4. 系統重新讀取該目標及條件的申請流程，只接受已發布、適用性已確認、年度／指定梯次一致，且有 HTTP(S) 來源、尚未過期的精確期限。
5. 呼叫既有 `/calendar/tasks/schedule`，按使用者的準備天數從期限往前計算日曆天，先顯示預覽與來源；確認後才保存到日曆。
6. 同一個期限重複操作不會再新增任務，已有天數與進度會保留。預覽後修改條件或天數，需要重新預覽。

紙本送達與官方最晚寄出時間分開處理。找不到可用期限時不猜日期，顯示原因並保留手動日曆入口。此功能沿用既有帳號與功能權限，不會自動開放原本受限的進階能力。

## 目前不是完整的 AI 自動規劃

`advisor.py::build_advisor_plan` 的學校排名主要是規則比對；AI 增強在有問題、且 AI 服務可用時才可能參與文字回答。本輪背景取得推薦不帶問題，不觸發 AI 問答。排名不是錄取機率；公開學院與語言資料不足、或條件不符時，仍須顯示缺口。

目前預算評分主要看生活資料是否已整理，尚未逐校計算「實際總成本是否落在個人預算內」。期限接受的是系統儲存的審核及適用性標記，不等於本輪已逐項上網或由真人重審來源；正式資料治理仍需另外驗證。

完整學業／語言條件目前仍依既有本機保存方式共用；現有帳號工作區可同步目標、學院、學系、學制與個人日曆任務，尚未擴充成可跨裝置保存完整選校條件的後端 schema。

下一輪最有價值的工作是：

- 統一搜尋頁與推薦引擎的資格判定，明確區分符合、條件不符、資料不足。
- 將「每項期限倒推 N 天」升級成文件依賴任務：語言證明、推薦信、讀書計畫、校內核章、寄件等，各自有準備時間。
- 加入使用者每週可投入時間、已有文件、預計出發學期，避免任務同時擠在一起；容量不足時讓使用者調整。
- 官方期限變更時顯示差異並讓使用者確認重新排程；本輪沒有自動覆蓋個人任務。
- 成本比較使用有年度、幣別、適用校區及來源的費用，資料不足時明確留白。
