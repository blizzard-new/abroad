# Web 討論板第二輪補齊（2026-09-30）

本輪修改 Web 與後端，沿用 UniWay 的視覺和交換申請情境。未移植 iOS、Android、Flutter；未部署或修改正式 Supabase、既有討論資料。

## 已完成

- **真正的回覆串**：留言保存 `parent_id`，採兩層結構（主留言／串內回覆）。回覆串按需展開、獨立分頁、失敗可重試；子留言的「回覆此串」仍回到同一主留言。不同文章、隱藏留言、不合法的第三層不能作為父留言。樓層不因刪除而重新編號。
- **對話與草稿**：文章回覆與各串草稿分開保存。作者刪除已有後續回覆的主留言時，保留刪除標示與後續對話；隱藏主留言會隱藏整串。作者刪除不能解除管理者的隱藏決定。
- **帳號反應**：文章、留言提供「有幫助／感謝」，同一帳號每份內容最多一種反應，可切換或取消。採用保存指定狀態的 PUT，重試不會反覆切換；未驗證、停權、校籍不符或內容未公開時禁止操作。公開回應不含反應者帳號或作者內部識別碼。
- **帳號收藏**：登入後收藏保存到後端，其他瀏覽器登入同帳號即可讀取；訪客收藏仍保存在此瀏覽器。帳號上限 100 篇。第一輪帳號本機收藏可按「同步此瀏覽器舊收藏」匯入，失敗時保留尚未完成的項目。刪除文章或帳號時會清除對應收藏。
- **管理工作台**：沿用伺服器設定的內容／平台管理員權限，提供待審核、已公開、已隱藏內容，核准、隱藏、1／7／30 天停權，以及檢舉原文檢視、處理、駁回。處理原因必填，操作留有稽核紀錄；衝突操作要求重新載入。停權到期自動恢復發言資格。
- **檢舉保存**：接回既有 repository 的原子檢舉與處理操作，包含帳號綁定、目標檢查、重試去重與稽核。檢舉的「已處理」不會自動隱藏原文，管理者需另作明確決定。
- **風險文字**：涉及保證錄取、保證簽證、付費代辦等關鍵字的文章／留言先進待審核。這是篩查規則，核准不代表系統保證內容真實。

## 驗證

- 75 項 pytest 通過：第二輪 API、並行／故障回滾、第一輪瀏覽、既有原子發布、repository、校籍存取、SQL 語法，以及 10 項瀏覽器流程。沒有跳過這組測試。
- 45 項隔離 PostgreSQL 行為與權限檢查通過，使用 PGlite 的 PostgreSQL 執行環境。套用 22 份相關 migration；獨立的 RAG/vector migration 未在此執行環境套用。檢查實際發布／重試、回覆關聯、反應、收藏、核准／隱藏衝突、停權、刪除清理，以及匿名／登入角色的拒絕存取。
- 23 份 migration 的 SQL 與函式內容皆通過語法解析。
- 三份 Web JavaScript 通過 `node --check`。
- 測試過程重現了兩個時序問題：帳號收藏的回應較慢時，舊搜尋狀態會覆蓋新輸入；登入視窗的延遲自動聚焦會把使用者已選好的密碼欄切回信箱。兩者已修正並新增回歸檢查，包含連續五次從文章進入登入。最後完整 75 項均通過。

重跑 SQL 行為檢查：在專案外的臨時目錄安裝 `@electric-sql/pglite`，執行 `node scripts/verify_discussion_sql.cjs <該目錄>`。此腳本只使用隔離記憶體資料庫，不連線正式資料庫。

## 部署前仍需完成

正式 Supabase 尚未套用 `20260930100000_discussion_threads_reactions.sql`。其新表開啟 RLS，撤銷匿名／登入角色的直接存取與 RPC 執行權限，透過既有 FastAPI 服務存取。部署時需保持後端與 migration 同步，再驗證正式環境的登入、管理員設定和帳號流程；本輪沒有驗證整個專案可上線。

管理內容、檢舉及稽核畫面目前顯示最近 100 筆，尚無完整管理端分頁與全文搜尋。兩層回覆是本輪的明確結構；不限層數留言、圖片上傳、即時通知、個人化熱門推薦不在本輪範圍。
