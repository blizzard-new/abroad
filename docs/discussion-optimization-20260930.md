# UniWay 討論板優化

本輪依據使用者提供的 `dcard_frontend_reverse_engineering.md`，借鏡瀏覽與狀態管理邏輯，保留 UniWay 的視覺與交換申請情境。文件內未驗證的 Dcard API、框架與操作步驟沒有當成已確認事實或執行指令。

## 已實作

| 操作 | 現在的行為 |
| --- | --- |
| 瀏覽列表 | 每頁 20 篇摘要，不預先傳送全文或留言；可自動接續載入，也保留手動按鈕 |
| 找到討論 | 搜尋、主題、排序與收藏篩選保存在網址，重新整理後可以接續 |
| 排序 | 最新、較早、待回覆；不將未實作的熱度演算法包裝成熱門排行 |
| 閱讀文章 | 可分享的獨立文章網址，閱讀視窗分開載入文章與留言；桌面置中、手機全螢幕 |
| 返回列表 | 保留搜尋、篩選、已載入頁次，使用既有導航的捲動恢復與安全返回邊界 |
| 留言 | 由舊到新／由新到舊、分頁、樓層、引用文字；留言載入失敗可獨立重試，文章仍可閱讀 |
| 寫作 | 發文／留言草稿保存在此分頁的 sessionStorage，按帳號分隔；成功發布後清除，失敗保留 |
| 收藏 | 最多 100 篇，按帳號／訪客分隔，保存在此瀏覽器，介面明示保存範圍 |
| 分享 | 優先使用系統分享，其次複製連結；權限不足時提供可手動複製的欄位 |
| 權限與發布 | 帳號身分、貼文及留言改走既有 community repository 的原子提交、限流與重試去重；維持 Email 與本校驗證限制 |
| 隱私 | 新瀏覽 API 不傳內部作者 ID；舊貼文列表保留欄位但清空 ID |

國家、申請年度、申請階段直接出現在文章摘要與內文。同學經驗保留提醒，申請資格與期限仍須核對官方公告。「待回覆」優先協助有問題的同學，適合 UniWay 的申請交流用途。

## 程式範圍

- `src/exchange_info/community_browsing.py`：獨立瀏覽 API、身分選項、原子發布適配；游標經簽章並綁定查詢條件與排序。
- `src/exchange_info/api.py`：串接瀏覽模組；替換帳號社群身分、發文、留言的本機直寫路徑；舊列表讀取 repository。
- `src/exchange_info/community_repositories.py`：本機 repository 延續伺服器指定的管理員跨校權限，管理員使用一般帳號限流額度。
- `src/exchange_info/static/community-reader.js`、`community-reader.css`：獨立閱讀、分頁、收藏、草稿與分享。
- `src/exchange_info/static/app.js`、`index.html`：沿用既有傳輸、帳號狀態、身分選擇、看板權限與視覺樣式，加入必要的控制與事件接口。
- `tests/test_community_browsing.py`、`tests/e2e/test_discussion_reader.py`：隔離資料的 API 與 Chromium 瀏覽器驗證。

這輪是 Web 改善，未移植 Flutter、iOS、Android，未部署正式環境，未改寫現有社群內容。

## 尚未納入與上線限制

1. **真正的巢狀留言、多種反應與跨裝置收藏尚未實作。** 目前的引用回覆是明確的文字引用，沒有虛構父子留言關係或反應數。新增這些功能需要資料庫 schema、原子更新與權限設計。
2. **管理者審核、停權、刪除與帳號刪除後去識別仍有既有缺口。** 部分對應路由不存在；高風險內容待審行為仍有失敗測試。本輪不代表討論板已達正式發布條件。
3. **Supabase 未做線上整合驗證。** 瀏覽與發布已接既有 repository/RPC；現有 SQL 的校籍驗證與新帳號限流尚未支援 Python 環境變數指定的管理員跨校例外，正式環境會拒絕不符合 SQL 規則的操作。需要正式部署前完成 DB 權限一致性設計。
4. **後端查詢仍使用 repository 的全量讀取。** 分頁降低 API 傳輸與 Web 渲染量，尚未改為資料庫層的條件查詢／游標。資料量大時應優先補 SQL 查詢、索引與適當讀取政策。
5. **游標以應用程式實例的金鑰簽章。** 重啟或切換到另一實例後會失效；列表提供重新載入。多實例部署前應改成伺服器共同設定的金鑰。分頁快照依建立時間，待回覆篩選會隨新的回覆變動。

## 下一批值得借鏡的改善

- 將官方學校資料、同學經驗、私人申請工作區分開快取與錯誤狀態，避免一個請求失敗拖垮整頁。
- 將帳號、收藏、追蹤、通知各自分開管理，避免登入／登出或帳號切換時沿用上一位使用者的狀態。
- 讓合作校比較、申請任務與經驗文章有可分享的穩定連結，搜尋條件可從網址恢復。
- 在完成審核工具與稽核後，再加入「有幫助／謝謝／一起加油」等符合留學交流情境的反應，避免只鼓勵情緒或流量。
- 先以真實用戶驗證待回覆、年份情境、草稿與回到列表的流程，再評估熱門排行與推薦排序。

## 驗證

使用 Windows 上的隔離暫存資料與專案既有 pytest／Chromium 測試環境；沒有以真實帳號或既有資料發文。涵蓋摘要與作者資訊邊界、隱藏內容、游標排序與篩選綁定、發布重試、驗證與停權限制、注入 repository，以及桌面／390px 手機的開文、分享網址、收藏、返回、引用、草稿、Cookie 留言與留言失敗重試。

本輪驗證：`46 passed`（10 個瀏覽／發布 API 案例、16 個 repository 案例、16 個校籍與目錄權限案例、4 個 Chromium 桌面／手機流程）。兩個 JavaScript 檔案通過 `node --check`。瀏覽器也驗證了從文章登入後回到原文留言，以及其他分頁更新社群憑證後安全重試留言。

另抽驗既有 `test_atomic_public_community_api.py`，4 個發布／原子行為案例通過；管理者停權路由缺失、高風險內容未進待審造成另外 2 個既有案例失敗。其他既有治理失敗不能視為本輪測試通過。Supabase 的線上資料庫與正式部署未驗證。

和實作前保存在專案外的原始檔比對，本輪新增差異沒有行尾空白。整個 dirty checkout 的 `git diff --check` 仍報告 `api.py` 四處原有行尾空白，沒有改動那些區塊。
